# Состояние проекта: Czech Business Model Radar

*Обновлено: 2026-09-26. Последний коммит: `8322c27` (результаты 10.1).*

Streamlit-приложение, которое собирает проверенные в мире модели малого бизнеса и микро-SaaS
и оценивает, насколько их можно адаптировать для Чехии (Прага, чешский МСП-сегмент).
Целевой рынок всегда Чехия; страна у модели означает, где она доказала себя.

---

## 1. Что было сделано (хронология)

### Этап A. Базовое приложение
- Streamlit-дашборд: фильтры, карта возможностей (скор × MRR 12-го месяца), карточки, «Разбор для Чехии»
  (Deep-Dive), таблица, методология, экспорт в Markdown и PDF (кириллица и чешская диакритика работают).
- Два движка отчёта: офлайн-эвристика (мгновенно, без ключа) и Claude (Anthropic SDK, structured outputs).
  При ошибке API — автоматический откат на офлайн-отчёт.
- Живые источники: Hacker News «Show HN» (Algolia API) и Product Hunt (RSS).
- README с инструкцией по деплою на Streamlit Community Cloud.

### Этап B. Gemini как второй LLM-провайдер
- `google-genai`, модели `gemini-2.5-flash` (по умолчанию), `gemini-2.5-pro`, `gemini-3.5-flash`
  и ввод любой другой. Режим «Авто»: Claude → Gemini → офлайн.

### Этап C. Рост базы: 30 → 100 → 500 моделей
- 100 моделей с вручную прописанными чешскими сегментами и конкурентами.
- +400 моделей из 64 стран (США, Европа, Россия, Украина, ЦВЕ, Азия, Латинская Америка, Африка)
  в пакете `catalog/`. Для них чешские конкуренты берутся из «ландшафта категории»
  (помечен как непроверенный), если не указаны явно.
- Добавлены категории: D2C и подписки, Здоровье и велнес, Образование и EdTech (всего 12).
- Исправлены завышения: разовые платежи, засчитанные как ежемесячные (Laba, налоговые декларации);
  добавлена себестоимость (COGS) для сервисных моделей (BetterHelp, Knopka, Skyeng, Kumon).

### Поток данных
1. `load_curated()` собирает 500 записей → `apply_cz_defaults()` накладывает оверлей и правила вывода
   (выведенные поля попадают в `inferred_fields`).
2. `quick_metrics()` → исходный скор выполнимости (6 факторов, веса 28/20/14/10/14/14 %) и MRR 12-го месяца.
3. `derived_metrics()` → нужное число клиентов, доля SAM, сопоставимость MRR.
4. `czech_adjusted_score()` → исходный скор минус: конкуренты (по силе), доля SAM (> 2 %),
   юридическая сложность, сложные интеграции (Pohoda, Money S3, ABRA, Bank iD, ISDOC),
   поддержка на чешском для соло-основателя. Сезонность даёт рекомендацию, а не штраф.
5. «Разбор»: офлайн-отчёт или LLM (получает эвристику и чешский контекст как базу).

### Ключевые принципы
- Базовые записи моделей не меняются: чешские данные и исправления — только через оверлей.
- Выведенное правилами всегда помечено; неизвестное остаётся пустым, а не придумывается.
- Внутренние ключи (категории, типы, колонки) на английском; перевод только при показе.
- API-ключи только из env / secrets / поля в сайдбаре (хранится в сессии браузера).

## 3. Решённые проблемы

| Проблема | Решение |
|---|---|
| `venv` не создавался / `source` не работает в cmd | Окружение уже было; активация `.venv\Scripts\activate` |
| Разовые платежи считались как ежемесячные (завышение MRR) | Пересчёт в месячный эквивалент + заметка |
| Не учитывалась оплата специалистов у сервисных моделей | Добавлен COGS |
| Неверные типы моделей (платёжные сервисы как маркетплейсы и т. п.) | Правила исправлены + 8 ручных поправок в оверлее |
| SAM «круговой»: клиенты = SAM × доля, поэтому доля SAM всегда ≤ 1 % | Реальный SAM из ČSÚ для 57 моделей |
| ČSÚ: «активные» включают спящих OSVČ (115 тыс. «ресторанов») | Для общепита сегмент «с сотрудниками» (24 тыс.) |

| Кафе и фитнес регистрируются под другими кодами | Коды 56.10 / 93.11 вместо 56.30 / 93.13 |
| Поиск ARES по CZ-NACE возвращает мусор | ARES не используется, решение задокументировано |
| Ложные срабатывания аудита (111 → 20) | Сравнение URL с названием без пробелов, архетипы исключены |
| Карта сжата по вертикали | Легенды перенесены вправо |
| AppTest не работал с `format_func` | Язык запуска захватывается в хелперах |
| Английские остатки в русском UI | Плейсхолдеры, «нет данных», десятичная запятая, разделители тысяч |

## 4. Известные методологические проблемы (не исправлены)

1. **Двойной учёт.** Исходный скор уже включает конкуренцию и регуляцию, а чешский скор снова
   вычитает конкурентов и юридическую сложность.
2. **Награда за отсутствие данных.** Штраф за конкурентов есть только там, где они заполнены.
   Верх рейтинга (Spond, Twinkl, Lalilo, Jobber) держится на «0 конкурентов».
3. **Правила завышают скор относительно Gemini** (данные из 4 прогонов):
   | Модель | Правила | Gemini | Конкуренты: правила → Gemini |
   |---|---|---|---|
   | 6AM City | 65 | 50 | 0 → 3 |
   | Slice | 53 | 45 и 53 (два прогона) | 0 → 4 |
   | Nicereply | 50 | 38 | 0 → 3 |
4. **Штраф за долю SAM у Spond = −0,38** (показывается как −0). Это не ошибка округления:
   кривая линейная от 2 % до 10 %, скачка на пороге нет.
5. **Штраф «поддержка на чешском»** стоит почти у всех (правило: B2C ИЛИ «локальная» категория ИЛИ moat ≥ 4).
6. **6AM City имеет тип `saas`**, хотя это рекламное медиа.
7. **Разброс LLM:** одна и та же модель (Slice) дала 53 и 45.
